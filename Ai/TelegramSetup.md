# راه‌اندازی اعلان تلگرام مدیر

## رفتار

نوبت جدید (مشتری یا پنل)، لغو نوبت توسط مشتری و سفارش محصول جدید، علاوه بر اعلان داخل برنامه، برای مدیر فعال و متصل همان سالن به تلگرام ارسال می‌شوند. هر مدیر می‌تواند گیرنده جداگانه داشته باشد. تغییر برنامه کارکنان و خطاهای فنی در این مرحله ارسال نمی‌شوند. اعلان‌های پیش از فعال‌سازی بازپخش نمی‌شوند.

## تنظیم

بات را در BotFather بساز و توکن را فقط در `.env` سرور وارد کن:

```dotenv
TELEGRAM_ENABLED=true
TELEGRAM_BOT_TOKEN=
TELEGRAM_PROXY_URL=
```

مقدار خالی را با توکن واقعی جایگزین کن. توکن را در مستندات، Git یا خروجی خطا قرار نده. مدیر باید ابتدا بات را در چت خصوصی Start کند؛ شناسه عددی کاربر/چت خصوصی لازم است، نه نام کاربری `@username`. توکن بات و شناسه تلگرام دو مقدار جدا هستند.

```sh
php artisan migrate
php artisan config:clear
php artisan telegram:connect ara APP_USER_ID TELEGRAM_NUMERIC_USER_ID
php artisan queue:work database --queue=telegram,default --timeout=30
```

`ara` اسلاگ سالن، `APP_USER_ID` شناسه حساب مدیر در برنامه و مقدار آخر شناسه عددی تلگرام اوست. فرمان فقط مدیر فعال سالن فعال را می‌پذیرد. اتصال مربوط به همان عضویت سالن است؛ شناسه تلگرام وارد پاسخ‌های API پروفایل نمی‌شود. وب‌هوک برای ارسال به گیرنده مشخص نیاز نیست. سرور باید HTTPS خروجی به `api.telegram.org` داشته باشد و Queue Worker در استقرار با Supervisor یا systemd دائماً اجرا شود. پس از تغییر کد یا تنظیمات، Workerها را با `php artisan queue:restart` راه‌اندازی مجدد کن. `composer dev` صف‌های mail، telegram و default را گوش می‌دهد؛ در اجرای مستقل، Worker بالا را اجرا کن.

برای آزمایش، پس از اتصال و اجرای Worker:

```sh
php artisan telegram:test ara APP_USER_ID
```

این فرمان پیام آزمایشی را صف می‌کند؛ نتیجه ارسال در `telegram_deliveries` با شناسه چاپ‌شده بررسی شود. لینک دکمه از `APP_URL` ساخته می‌شود؛ برای استفاده روی گوشی باید آدرس قابل دسترس پنل تنظیم شود. دریافت پیام تنها پس از آزمایش واقعی با توکن و گیرنده تأیید می‌شود.

## خطا و تلاش مجدد

جدول `telegram_deliveries` سابقه شامل pending، sent، failed یا skipped، تعداد تلاش، کد خطا، شناسه پیام و زمان ارسال دارد. درخواست‌ها پس از Commit وارد صف database/telegram می‌شوند؛ Rollback اعلان بیرونی ندارد. HTTP timeout و ۵xx با فاصله افزایشی تا ۵ تلاش تکرار می‌شوند؛ ۴۲۹ زمان `retry_after` تلگرام را رعایت می‌کند. خطاهای دائمی مانند ۴۰۳ به failed تبدیل می‌شوند. دسترسی و گیرنده پیش از ارسال دوباره بررسی می‌شوند؛ تغییر عضویت یا گیرنده، پیام قدیمی را skipped می‌کند. متن پاسخ سرویس و توکن ذخیره نمی‌شوند.

بعد از رفع مشکل می‌توان pending یا failed را مجدداً صف کرد:

```sh
php artisan telegram:retry DELIVERY_ID
```

رکورد sent مجدداً ارسال نمی‌شود و قفل Worker از ارسال هم‌زمان یک رکورد جلوگیری می‌کند. در حالت قطع ارتباط پس از پذیرش پیام توسط تلگرام و پیش از ثبت موفقیت در دیتابیس، تکرار پیام در Retry ممکن است؛ Bot API تضمین Exactly Once ندارد. اگر ثبت Job پس از Commit شکست بخورد، رکورد pending باقی می‌ماند و فرمان retry آن را بازیابی می‌کند.

قطع اتصال:

```sh
php artisan telegram:connect ara APP_USER_ID TELEGRAM_NUMERIC_USER_ID --disconnect
```

مرجع: [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

## شبکه محدود و پروکسی

اگر اتصال مستقیم تلگرام ممکن نیست، `TELEGRAM_PROXY_URL` را به پروکسی فعال HTTP یا SOCKS (برای نمونه `http://127.0.0.1:10808` یا `socks5h://127.0.0.1:10808`) تنظیم کن. پورت و پروتکل باید مطابق سرویس واقعی باشند. سپس config:clear و queue:restart اجرا شوند. برای SOCKS افزونه curl در PHP لازم است. TLS فعال می‌ماند؛ با خاموش‌کردن بررسی گواهی، مشکل اتصال حل نشود. پروکسی فقط روی درخواست‌های تلگرام اعمال می‌شود. اطلاعات احراز هویت پروکسی نیز فقط در محیط نگهداری شوند.

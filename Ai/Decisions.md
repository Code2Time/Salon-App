# تصمیم‌ها و ابهام‌ها

این فایل تفاوت «نیازمندی»، «پیشنهاد» و «تصمیم پذیرفته‌شده» را حفظ می‌کند. تصمیم جدید با تاریخ، وضعیت، دلیل و اثر بر Database/API/UI ثبت شود؛ تصمیم جایگزین‌شده حذف نشود و به جایگزین ارجاع بدهد.

## الزامات تثبیت‌شده در BasePrompt

- Laravel API و React + TypeScript + Vite + MUI.
- رابط فارسی و RTL؛ Theme مرکزی و معماری ماژولار.
- توسعهٔ مرحله‌ای و آمادگی جداسازی داده‌های چند سالن از ابتدا.
- مدت خدمت، برنامهٔ کارکنان و قوانین قابل تنظیم، مبنای رزرو هستند.

## تصمیم پذیرفته‌شده — احراز هویت، نقش و زمینهٔ سالن

- تاریخ: 2026-10-08؛ مرجع: اجرای تسک 01b و تصمیم‌های کاربر.
- ورود و ثبت‌نام با موبایل ایرانی و OTP انجام می‌شود. شماره هم در Database و هم در API با قالب یازده‌رقمی `09xxxxxxxxx` نگهداری می‌شود؛ ورودی قدیمی `+98` نیز پیش از ذخیره به همین قالب تبدیل می‌شود.
- OTP ثابت `1111` فقط Provider محیط `local` و `testing` است؛ در محیط دیگر این Provider عمداً خطا می‌دهد. اتصال پیامک واقعی هنوز انجام و تأیید نشده است.
- ثبت‌نام یک جریان صریح و جدا از Login است و فقط کاربر مشتری بدون دسترسی پنل می‌سازد. نقش ورودی کاربر پذیرفته نمی‌شود.
- `super_admin` نقش سراسری و دارای دسترسی همهٔ سالن‌هاست. نقش‌های `salon_owner`، `manager` و `employee` روی عضویت کاربر در سالن نگهداری می‌شوند؛ مشتری عضویت مدیریتی ندارد.
- نسخهٔ فعلی روی یک سالن متمرکز است، ولی `salons` و `salon_user` و Header اختیاری `X-Salon-ID` زمینهٔ چندسالن را آماده می‌کنند. Backend عضویت سالن را بررسی می‌کند و شناسهٔ ارسالی کاربر را قابل اعتماد نمی‌داند.
- Super Admin و اعضای فعال سالن وارد `/panel` می‌شوند؛ مشتری وارد `/app` می‌شود. منوی کارمند به داشبورد و نوبت‌ها محدود است، Manager به‌جز تنظیمات سالن به بخش‌های پنل دسترسی دارد و Owner و Super Admin همهٔ صفحات فعلی پنل را می‌بینند.
- SPA با Laravel Sanctum و Session/Cookie احراز می‌شود. Session در محیط پروژه ۹۰۰ دقیقه (۱۵ ساعت) اعتبار دارد و شناسهٔ Session پس از ورود بازتولید می‌شود.
- MySQL دیتابیس هدف است. تست‌ها برای جداسازی از دیتابیس توسعه روی SQLite حافظه‌ای اجرا می‌شوند.

## تصمیم پذیرفته‌شده — مدیریت کاربران پنل سالن

- تاریخ: 2026-10-10؛ مرجع: آغاز فاز 02 از نقش مدیر سالن و CRUD کاربران.
- User هویت سراسری فرد است و دسترسی پنل، نقش و وضعیت او در هر سالن روی `salon_user` نگهداری می‌شود. شماره موبایل در سطح سیستم یکتا باقی می‌ماند.
- فقط مالک فعال سالن و Super Admin اجازه CRUD عضویت‌های پنل را دارند. Manager و Employee نمی‌توانند نقش‌ها را مدیریت کنند.
- حذف کاربر از سالن Soft Delete روی User نیست؛ عضویت همان سالن غیرفعال می‌شود تا حساب و سوابق مشترک حذف نشوند. آخرین مالک فعال قابل غیرفعال‌سازی یا تنزل نیست.
- ستون `users.deleted_at` برای حذف نرم سراسری حساب اضافه شد. این قابلیت مستقل از حذف دسترسی یک سالن است و CRUD فعلی سالن برای جلوگیری از اثر بین‌سالن‌ها User را Soft Delete نمی‌کند.
- API شناسه سالن را از payload دریافت نمی‌کند و همه عملیات پس از Resolve شدن Salon Context اجرا می‌شوند.

- در اپ مشتری اصطلاح «خدمات» استفاده می‌شود و اصطلاح مدیریتی پنل «سرویس‌ها» باقی می‌ماند. کارت اولیه قیمت و معرفی کوتاه دارد؛ مدت و متخصصان فقط در جزئیات دیده می‌شوند تا انتخاب متخصص در جریان رزرو آینده به همان بخش افزوده شود.

## تصمیم پذیرفته‌شده — ثبت خطاهای Backend در دیتابیس

- تاریخ: 2026-10-10؛ مرجع: درخواست کاربر برای نگهداری خطاها پیش از اتصال Telegram.
- خطاهای غیرمنتظره و پاسخ‌های ۵۰۰ به بالا در `error_logs` ثبت می‌شوند؛ ۴xxهای عمومی ثبت نمی‌شوند، اما خطاهای دامنه‌ای منتخب که برای امنیت و پشتیبانی مهم‌اند، مانند OTP اشتباه/منقضی یا وضعیت نامعتبر حساب در جریان تأیید، با وضعیت ۴۲۲ ثبت می‌شوند.
- برای حفظ امنیت، payload، query string، header، Cookie و token ذخیره نمی‌شوند و پیام Exception پیش از ذخیره برای الگوهای حساس و موبایل پاک‌سازی می‌شود.
- رکورد شامل `reference_id` یکتا، محیط، Exception، مسیر بدون query، کاربر و سالن nullable، محل کد، Stack Trace و `resolved_at` است.
- ارسال هشدار خارجی، UI مدیریت خطا و سیاست retention به تسک‌های آینده واگذار شدند.

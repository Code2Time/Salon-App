# تصمیم‌ها و ابهام‌ها

این فایل تفاوت «نیازمندی»، «پیشنهاد» و «تصمیم پذیرفته‌شده» را حفظ می‌کند. تصمیم جدید با تاریخ، وضعیت، دلیل و اثر بر Database/API/UI ثبت شود؛ تصمیم جایگزین‌شده حذف نشود و به جایگزین ارجاع بدهد.

## الزامات تثبیت‌شده در BasePrompt

- Laravel API و React + TypeScript + Vite + MUI.
- رابط فارسی و RTL؛ Theme مرکزی و معماری ماژولار.
- توسعهٔ مرحله‌ای و آمادگی جداسازی داده‌های چند سالن از ابتدا.
- مدت خدمت، برنامهٔ کارکنان و قوانین قابل تنظیم، مبنای رزرو هستند.

## تصمیم پذیرفته‌شده — احراز هویت، نقش و زمینهٔ سالن

- تاریخ: 2026-10-08؛ مرجع: اجرای تسک 01b و تصمیم‌های کاربر.
- ورود و ثبت‌نام با موبایل ایرانی و OTP انجام می‌شود. شماره هم در Database و هم در API با قالب یازده‌رقمی `09xxxxxxxxx` نگهداری می‌شود؛ ورودی قدیمی `+98` نیز پیش از ذخیره به همین قالب تبدیل می‌شود.
- OTP ثابت `1111` فقط Provider محیط `local` و `testing` است؛ در محیط دیگر این Provider عمداً خطا می‌دهد. اتصال پیامک واقعی هنوز انجام و تأیید نشده است.
- ثبت‌نام یک جریان صریح و جدا از Login است و فقط کاربر مشتری بدون دسترسی پنل می‌سازد. نقش ورودی کاربر پذیرفته نمی‌شود.
- `super_admin` نقش سراسری و دارای دسترسی همهٔ سالن‌هاست. نقش‌های `salon_owner`، `manager` و `employee` روی عضویت کاربر در سالن نگهداری می‌شوند؛ مشتری عضویت مدیریتی ندارد.
- نسخهٔ فعلی روی یک سالن متمرکز است، ولی `salons` و `salon_user` و Header اختیاری `X-Salon-ID` زمینهٔ چندسالن را آماده می‌کنند. Backend عضویت سالن را بررسی می‌کند و شناسهٔ ارسالی کاربر را قابل اعتماد نمی‌داند.
- Super Admin و اعضای فعال سالن وارد `/panel` می‌شوند؛ مشتری وارد `/app` می‌شود. منوی کارمند به داشبورد و نوبت‌ها محدود است، Manager به‌جز تنظیمات سالن به بخش‌های پنل دسترسی دارد و Owner و Super Admin همهٔ صفحات فعلی پنل را می‌بینند.
- SPA با Laravel Sanctum و Session/Cookie احراز می‌شود. Session در محیط پروژه ۹۰۰ دقیقه (۱۵ ساعت) اعتبار دارد و شناسهٔ Session پس از ورود بازتولید می‌شود.
- MySQL دیتابیس هدف است. تست‌ها برای جداسازی از دیتابیس توسعه روی SQLite حافظه‌ای اجرا می‌شوند.

## تصمیم پذیرفته‌شده — مدیریت کاربران پنل سالن

- تاریخ: 2026-10-10؛ مرجع: آغاز فاز 02 از نقش مدیر سالن و CRUD کاربران.
- User هویت سراسری فرد است و دسترسی پنل، نقش و وضعیت او در هر سالن روی `salon_user` نگهداری می‌شود. شماره موبایل در سطح سیستم یکتا باقی می‌ماند.
- فقط مالک فعال سالن و Super Admin اجازه CRUD عضویت‌های پنل را دارند. Manager و Employee نمی‌توانند نقش‌ها را مدیریت کنند.
- حذف کاربر از سالن Soft Delete روی User نیست؛ عضویت همان سالن غیرفعال می‌شود تا حساب و سوابق مشترک حذف نشوند. آخرین مالک فعال قابل غیرفعال‌سازی یا تنزل نیست.
- ستون `users.deleted_at` برای حذف نرم سراسری حساب اضافه شد. این قابلیت مستقل از حذف دسترسی یک سالن است و CRUD فعلی سالن برای جلوگیری از اثر بین‌سالن‌ها User را Soft Delete نمی‌کند.
- API شناسه سالن را از payload دریافت نمی‌کند و همه عملیات پس از Resolve شدن Salon Context اجرا می‌شوند.

- فقط ثبت Completed پیشنهاد می‌سازد؛ گذشت زمان، لغو، عدم حضور و Pending محرک نیستند. مدیر می‌تواند انجام واقعی نوبت Expired را ثبت کند؛ کارکنان اجازه این تبدیل پس از انقضا ندارند. نوبت‌هایی که قبل از این قابلیت Completed شده‌اند خودکار backfill نمی‌شوند.
- برای هر نوبت/محصول یک پیشنهاد شخصی با توضیح تمام خدمات مرتبط ساخته می‌شود. در چند ارتباط، بیشترین درصد فعال انتخاب می‌شود و درصدها جمع نمی‌شوند. فقط یک اعلان داخل برنامه برای مجموعه پیشنهادهای همان نوبت ساخته می‌شود؛ این رویداد اعلان خارجی مدیر نیست.
- مدت اعتبار بر حسب روز در تنظیمات عمومی سالن، بین ۱ تا ۳۶۵ روز، با مقدار اولیه ۷ تعیین می‌شود. توضیح، درصد و expires_at هنگام صدور ثابت‌اند؛ تغییر بعدی تنظیمات/درصد/خاموش‌کردن ارتباط، کد صادرشده را عوض نمی‌کند. قیمت روز، فعال‌بودن محصول/سالن و موجودی هنگام خرید دوباره کنترل می‌شوند.
- هر کد فقط متعلق به یک مشتری، یک سالن و یک محصول است و یک بار در ثبت موفق سفارش مصرف می‌شود؛ quote و افزودن به سبد آن را مصرف نمی‌کنند. یک استفاده یعنی یک سفارش شامل تعداد انتخاب‌شده همان محصول؛ تخفیف سایر محصولات سبد صفر است. سفارش فقط یک کد می‌پذیرد و ترکیب چند کد یا چند درصد وجود ندارد.
- تخفیف هر واحد، بخش صحیح قیمت×درصد/۱۰۰ به تومان است و در تعداد ضرب می‌شود؛ قیمت نمایش‌داده‌شده یک واحد با محاسبه سفارش سازگار است. سفارش و اقلام، قیمت عادی، تخفیف و مبلغ نهایی را حفظ می‌کنند. موجودی، ساخت سفارش و redeemed_at اتمیک‌اند؛ قفل و Unique Constraint از مصرف دوباره جلوگیری می‌کنند. Retry UUID یکسان همان سفارش را برمی‌گرداند.
- چون کاربر استفاده واقعی کد را خواست، اتصال محدود تخفیف به سبد و سفارش موجود به دامنه 06b افزوده شد؛ درگاه پرداخت، موتور عمومی کمپین‌ها، لغو سفارش/بازگرداندن کد و بازپرداخت در این تسک نیستند. محصول پیشنهادی فاقد تخفیف یا کد منقضی/مصرف‌شده با قیمت عادی قابل سفارش است؛ محصول ناموجود/غیرفعال/حذف‌شده پیشنهاد قابل دریافت ندارد.

## تصمیم پذیرفته‌شده — انتخاب چند خدمت در فرم محصول

- تاریخ: 2026-10-22؛ مرجع: گزارش کاربر درباره بسته‌شدن فهرست خدمات پس از هر انتخاب.
- لیست چندانتخابی خدمات مرتبط با `disableCloseOnSelect` باز می‌ماند؛ کاربر چند خدمت را در همان بازشدن انتخاب می‌کند و بستن با کلیک بیرون/Escape طبق رفتار استاندارد حفظ می‌شود.

## تصمیم پذیرفته‌شده — نصب اپ مشتری و به‌روزرسانی

- تاریخ: 2026-10-22؛ مرجع: درخواست نصب برنامه روی گوشی مشتری.
- نسخه نصب‌شدنی PWA از همان اپ React و نشست ورود موجود استفاده می‌کند؛ APK و فروشگاه اضافه نمی‌شوند. `/app/install` عمومی است و راهنمای Android و iOS، وضعیت پنجره مستقل و امکان نصب مرورگر را نمایش می‌دهد. manifest نام و آیکن را از هویت سالن فعال می‌گیرد؛ نبود لوگو آیکن عمومی دارد.
- نصب کامل و Service Worker به HTTPS معتبر یا localhost نیاز دارند؛ HTTP روی IP شبکه برای مرور سایت کافی است. لینک عمومی یا Tunnel خودکار ایجاد نمی‌شود و نصب، نیاز به روشن‌بودن میزبان را حذف نمی‌کند.
- Service Worker فقط در Build و از بخش مشتری ثبت می‌شود. فقط فایل‌های ثابت هش‌دار و صفحه عمومی قطع اتصال Cache می‌شوند؛ HTML مشتری، API، داده حساب، سفارش و پاسخ احراز هویت Cache نمی‌شوند و نوشتن آفلاین وجود ندارد.
- نسخه worker با manifest خروجی Build، کد worker و صفحه آفلاین نسخه‌گذاری می‌شود. نسخه جدید برای اقدام کاربر منتظر می‌ماند تا وسط فرم رزرو Reload خودکار رخ ندهد. داده Cache قدیمی فقط در فضای نام همین برنامه پاک می‌شود.

## اصلاح پذیرفته‌شده — جابه‌جایی فرم ورود و ثبت‌نام

- تاریخ: 2026-10-22؛ مرجع: گزارش باقی‌ماندن فرم کد ورود هنگام رفتن کاربر ثبت‌نام‌نشده به ثبت‌نام.
- Routeهای ورود و ثبت‌نام کلید مستقل دارند تا مرحله کد و مشخصات فرم قبلی باقی نمانند. فقط شماره معتبر و مقصد مشتری با state مسیریاب منتقل می‌شوند؛ کد تأیید انتقال یا ذخیره دائمی نمی‌شود.
- پاسخ دیرهنگام صفحه ترک‌شده اجازه تغییر مرحله، اعلان موفقیت/خطا یا انتقال کاربر از صفحه جدید ندارد. ثبت‌نام همچنان مشخصات و تأیید شماره می‌خواهد و خطای نبود حساب در ورود باعث ثبت‌نام خودکار نمی‌شود.
